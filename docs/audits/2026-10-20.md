## Summary

The server side is mostly well built:

- Every server action checks authorization itself.
- The two-approver rule holds against the obvious attacks: self-approval, double approval, self-demotion and removing the last admin.
- Sessions live in the database, so a demoted admin loses access on their next request.
- No secrets have ever been committed.

The serious problems were ones that only show up when you run the flows:

1. **An admin who had created any event could never be demoted.** libsql enforces foreign keys, and `events.created_by_admin_id` blocked the delete. Any admin could make themselves irremovable by creating one event. *Fixed.*
2. **A demoted seed admin is re-promoted at their next sign-in** while their email is still in `ADMIN_SEED_EMAILS`. That quietly undoes a two-approver removal. *Fixed 2026-10-21: auth.ts seeds through `seedAdminIfEligible`.*
3. **Every recurring event showed an hour off for part of the year.** The expansion stepped UTC instants instead of local dates. A weekly 1:30 PM Jummah created in January showed at 2:30 PM from March to November. *Fixed.*
4. **next 16.2.3 and next-auth 5.0.0-beta.31 had critical advisories.** These included two RCEs in Next and an Auth.js auth check that can fail open. *Fixed:* `bun audit` went from 82 advisories (6 critical, 42 high) to 2 dev-only ones with no fix available.

## Verified, no issue

- **Server actions authorize themselves.** All six admin actions call `requireAdminId()`. This matters because any action can be POSTed to any route, where `proxy.ts` doesn't run. The two RSVP actions require a session user id and only touch that user's rows.
- **IDOR.** Any admin may edit or delete any event; that is the documented trust model in `_actions.ts`. `cancelNomination` checks that the caller is the nominator. No route reads another user's data.
- **Governance rules hold:**
  - The nominator can't approve their own nomination: checked when approving and when tallying.
  - Nobody can approve twice: the primary key plus an explicit check.
  - An admin can't nominate themselves for demotion.
  - The last admin can't be removed: a count check, plus a recheck after the delete inside the transaction.
  - Only two paths add admins: an approved nomination, and seeding (#20).
- **Sessions and cookies.** Sessions live in the database (default 30 days), and `isAdmin` and `adminId` are re-read from `admins` on every request. Cookies use Auth.js defaults: HttpOnly, SameSite=Lax, and Secure with a `__Secure-` prefix over HTTPS. Account linking by email is off. Local `AUTH_SECRET` is a real 44-character value; the value in Vercel can't be checked from here.
- **Redirects and errors.** `/login` keeps `callbackUrl` to same-origin paths, and Auth.js's redirect callback does the same. Error codes map to fixed messages and nothing is echoed back.
- **CSRF.** Next checks Origin against Host on server actions. Auth.js uses a CSRF token for sign-in and sign-out. The only custom route handler is a GET.
- **Error leakage.** Actions return zod messages or fixed codes. Unexpected errors are masked by Next in production.
- **Secrets.** Nothing secret is in any commit. `.env*` is gitignored except the example file. The only `NEXT_PUBLIC_` variable is `SITE_URL`.
- **XSS in JSON-LD.** Event JSON-LD escapes `<`.

## Pending the auth.ts ruling — patches

*Updated 2026-10-21.* Justin asked for his gmail to be able to sign in as an admin, so the committed auth.ts changed (branch `auth-extra-emails`):

- **Extra addresses come from `AUTH_EXTRA_ALLOWED_EMAILS`.** Each is an exact, comma-separated address, and it gets in only when Google reports it verified (`isAllowedSignIn` in `lib/auth-policy.ts`). The `@ucsc.edu` rule is unchanged for everyone else. Production lists Justin's gmail there and in `ADMIN_SEED_EMAILS`. Granting `ucsc.msa@gmail.com` (#22) is now an env change, not a code change; it is still midna's decision.
- **Patch 1 (#20) is applied.** Seeding goes through `seedAdminIfEligible`, which skips anyone in `admin_removals`. Tests: `test/auth-signin.test.ts` runs auth.ts's own callbacks, and `_governance.test.ts › seedAdminIfEligible` covers the removal.
- **Patch 2 (#21) was regenerated against the new auth.ts.** It still waits, because it changes who can sign in, and only a real UCSC sign-in can confirm that Google sends `hd: "ucsc.edu"` for every current admin. There is one variant now; an empty `AUTH_EXTRA_ALLOWED_EMAILS` plays the part of `-no-gmail`.

```bash
git apply docs/audits/patches/auth-2-signin-policy.patch           # finding 21
```

`auth-2-signin-policy.patch`: requires `email_verified` and `hd === "ucsc.edu"`; the extra addresses keep their exact, verified match.

```diff
-import { isAllowedSignIn, parseEmailList } from "@/lib/auth-policy";
+import { isAllowedGoogleSignIn, parseEmailList } from "@/lib/auth-policy";
@@
-      if (!isAllowedSignIn(user.email, profile, extraAllowedEmails)) return false;
+      // Verified address in UCSC's Google Workspace (hd), not just the suffix.
+      if (!isAllowedGoogleSignIn(profile, extraAllowedEmails)) return false;
```

With no extra addresses, the Google provider could also take `authorization: { params: { hd: "ucsc.edu" } }`, so Google's account chooser offers only UCSC accounts. That is a UX nicety; the server-side check is what enforces the rule.

- **The event import API (step 4) adds migration `drizzle/0003_event_import.sql`.** It also must run on production before deploy, after 0002; running the migrator once applies both. It only adds columns, two tables and an index. `test/migrations.test.ts` runs it over seeded data.

- **`NEXT_PUBLIC_SITE_URL` in Vercel Production must be unset, or exactly `https://ucscmsa.com`.** Canonical URLs, `og:url`, the sitemap and robots.txt are all built from it. (Added with Frontend's SEO step; `GOOGLE_SITE_VERIFICATION` and `BING_SITE_VERIFICATION` are optional.)
